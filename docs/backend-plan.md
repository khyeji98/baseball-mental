# 서버 구성과 데이터 검증

2026-10-29 기준. 서버는 아직 배포하지 않았다. 앱은 샘플 데이터를 사용한다. 모노레포의 `apps/server`에 FastAPI·MongoDB 연결, 과거 경기 검증용 저장·조회 API, 수동 수집 작업을 구현했다. 운영 자동 수집·정규화·개인 기록은 미완료다. [실행 방법](../apps/server/README.md)을 참고한다.

## 결정

- Python/FastAPI API와 수집 작업을 분리한다. MongoDB/Beanie 기반 저장 모델은 유지한다.
- 초기 호스팅 기준안은 Cloud Run이다. AWS 전체 이전은 아직 결정하지 않는다.
- AWS Lambda + EventBridge Scheduler는 HTTP 기반 단기 수집 작업의 비교 후보로 유지한다.
- 데이터 수집은 경기별로 서버가 공유한다. 사용자마다 KBO 원본을 요청하지 않는다.
- 앱 화면에 원본 수집 시각과 지연 상태를 표시한다. 수집 실패를 경기 이벤트 없음으로 해석하지 않는다.

## 비용 비교의 전제

월 30일, 하루 5경기, 경기당 4시간, 60초 주기라면 월 36,000 경기 수집 회차다.
회차마다 엔드포인트 2개를 요청하면 원본 HTTP 요청은 72,000회다. 이용자 수와 무관하며 일정 조회·재시도는 별도다.
요청 빈도가 허용된다는 의미는 아니며, 실제 수집 운영 전 제공처 조건을 확인한다.

아래는 비교용 미국 리전 공개 단가에 따른 **수집 컴퓨팅만**의 계산이다. 서울 리전 최종 견적이나 서비스 전체 청구 예상액이 아니다.

| 방식 | 가정 | 무료량 적용 전 월 계산 |
|---|---|---|
| Lambda | 회차당 512MiB, 2초, 36,000회 | 36,000 GB-s × $0.0000166667 + 요청 $0.0072 ≈ $0.61 |
| Cloud Run 요청 기반 | 회차당 1vCPU, 512MiB, 2초, 36,000회; 콜드스타트 제외 | CPU $1.728 + 메모리 $0.09 + 요청 $0.0144 ≈ $1.83 |

무료량 잔여분이 충분하면 양쪽 모두 이 규모의 컴퓨팅 요금이 0이 될 수 있다. 계정 전체 사용량, 크레딧, 리전 단가와 실제 실행시간은 미확인이다. Lambda의 위 계산은 60초 대기를 함수 안에서 수행하지 않는 조건이다.

DB, API 트래픽, 스케줄러, 이미지 저장·전송, 빌드 이미지 저장소, 로그, 백업, 세금은 위 계산에서 제외했다. 따라서 전체 서버 무료 운영을 보장하지 않는다.

Lightsail은 공개 IPv4 포함 Linux 최소 사양이 월 $5부터이며 사용량이 적어도 고정 비용이 생긴다. 최소 사양에 API·수집기·MongoDB를 함께 배치하는 방안은 메모리와 백업 검증 없이 채택하지 않는다. 현재 규모에서는 서버 관리 부담까지 감수할 만큼 절감 근거가 없다.

Cloud Run은 최소 인스턴스 0, 수집 호출은 별도 스케줄러에서 인증하여 실행하는 구성을 기준으로 한다. 요청 처리 프로세스 안에 상시 타이머를 두지 않는다. Lambda 후보는 DB 네트워크 접근 방식까지 포함해 평가한다. 고정 출구 IP가 필요해 NAT 등이 추가되면 다시 계산한다.

출처: [Lambda 가격](https://aws.amazon.com/lambda/pricing/), [Cloud Run 가격](https://cloud.google.com/run/pricing), [Lightsail 가격](https://aws.amazon.com/lightsail/pricing/), [EventBridge 가격](https://aws.amazon.com/eventbridge/pricing/).

## 직접 확인한 데이터 접근 결과

KBO 공개 일정 페이지의 AJAX 요청 형식을 확인하여 2026년 9월 일정 응답 108행을 받았다. 일반 POST는 오류 HTML로 반환됐고, 페이지의 AJAX 요청 헤더를 적용한 요청에서 JSON을 받았다. HTTP 성공 여부만으로 수집 성공을 판정하면 안 된다.

공개 일정에서 확인한 경기 ID로 문자중계와 스코어를 조회했다.

| 경기 ID | 파싱된 문자중계 항목 | 원정:홈 최종 득점 |
|---|---:|---|
| 20260901LGOB0 | 475 | 3:1 |
| 20260901LTSS0 | 501 | 0:3 |
| 20260901HHKT0 | 549 | 1:6 |

항목 수는 투구·안내 등을 포함한 HTML 텍스트 수이며, 타석 수나 완전성 검증 결과가 아니다. 아직 선수 ID 연결, 사건 직전 아웃·주자·점수 복원, 기록 정정, 실시간 지연은 검증하지 않았다.

재현 명령은 경기당 두 요청만 실행한다. 자동 반복·프록시·접근 제한 우회는 포함하지 않는다. 원본 응답은 저장소에 배포하지 않는다.

```sh
cd apps/server
uv run python -m workers.probe_kbo 20260901LGOB0
```

참고: [KBO 일정](https://www.koreabaseball.com/Schedule/Schedule.aspx), [KBO 이용약관](https://www.koreabaseball.com/Etc/Policy.aspx). 기술적 응답 성공은 서비스에서 재이용할 권리 확보와 별개다.

## 구현 순서와 통과 조건

1. **데이터 의미 검증:** 위 3경기에서 최소 30타석을 대조한다. 이벤트 전후 상황, 선수 귀속, 실책·병살·득점의 구분을 검증한다. 중계로 판정할 수 없는 호수비를 임의 추정하지 않는다.
2. **수집 안정성 검증:** 실제 경기에서 수집 지연을 측정하고 5분 중단 후 복구, 중복 입력, 원본 기록 정정을 검증한다. 원본 갱신 시각이 없으면 실제 경기 시점 기준 지연을 측정했다고 표현하지 않는다.
3. **API·DB 계약:** 경기, 정규화 이벤트, 원본 버전, 팀 관점별 지수, 사용자 경기 기록, 푸시 구독을 정의한다. 이벤트 안정 키와 수정 이력을 보존하고 정정 시 관련 집계를 재계산한다.
4. **서버 구현:** 조회 API, 수집 작업, 영속 저장, 시즌·선수 집계, 경기 전 알림 작업을 구현한다. 배포 전 인증·접근 범위·중복 발송 방지를 검증한다.
5. **앱 연결:** 합의한 다크 테마와 Bagel 제목 서체, 구장·응원석 시점·팀 색상을 반영하고 실제 API로 연결한다. 구장 이미지 및 응원석 매핑은 확인된 자료만 사용한다.
6. **실기기·출시:** iOS/Android 알림과 진입·기록 저장을 검증한 뒤 실제 화면으로 스토어 스크린샷을 만든다. 콘셉트 시안을 구현 완료 화면으로 제출하지 않는다.

데이터 의미·안정성·재이용 조건이 해결되기 전 자동 경기 기록 기능을 출시 완료로 표시하지 않는다.
